### Critical gaps found in the import

1. **`src/styles.css` was missing** — every component references custom classes
   (`site-header`, `hero-photo`, `route-card`, `workspace`, …) that only existed in that file. The app could
   not build. → Reconstructed from the class inventory.
2. **`src/router.ts` was missing** — TanStack Start requires a router entry; the build failed to resolve it.
3. **`src/server.ts` was missing** — referenced by `vite.config.ts` (`tanstackStart.server.entry = "server"`).
   `src/lib/error-capture.ts` and `src/lib/error-page.ts` exist purely to support it.
4. **`src/client.tsx` / `src/start.ts` were missing** — optional entries; recreated.
5. **Both images were zero bytes** (`src/assets/arch-gym.jpg`, `src/assets/climbing-shoes.jpg`) — every hero and
   product image was broken. → Placeholder artwork generated by `scripts/generate_placeholder_images.py`.
6. **`public/favicon.svg` was missing** although `__root.tsx` links to it.
7. **`drizzle/schema.ts` is empty** and there are no migrations — the Drizzle/Supabase scaffolding is inert.
8. **All data is mock.** `src/services/arch.ts` is a hard-coded mock adapter; the UI labels itself
   "sample data / preview" throughout.
9. **`bun run lint` failed on the import** — 432 `prettier/prettier` errors (compact one-line style vs. the
   repository Prettier config, plus CRLF line endings). Fixed by normalising formatting.
10. **`.env` contains a real Supabase project key** and is git-ignored, but there was **no `.env.example`**.

- `uv run ruff check .` → clean. `uv run ruff format --check .` → 42 files
  already formatted.
- `uv run pytest` → **114 passed**.
- `uv run alembic upgrade head` on an empty database → applies cleanly;
  `uv run alembic current` → `c41ce9aba698 (head)`; `uv run alembic check` →
  "No new upgrade operations detected" (models and migration agree);
  `uv run alembic downgrade base` → clean rollback, then re-upgrade.
- `uv run python -m app.seed --reset --demo` → schema created through Alembic
  and seeded; running it twice does not duplicate rows.
- Live API smoke test against `http://localhost:8000`: `/api/health`,
  `/api/public/*`, `/api/auth/login` (demo customer), `/api/me/dashboard`,
  `/api/me/agreement`, `/api/me/leaderboard`, `/api/assistant/chat` all
  returned the expected payloads.

**Security review — issues found and fixed**

- The production secret-key check only matched the exact string
  `"production"`. → now case-insensitive and also matches `"prod"`, and it is
  covered by a test that uses the environment variable.
- `CORS_ORIGINS=*` would have been combined with credentialed requests. →
  a wildcard is now rejected at start-up.
- Passwords longer than bcrypt's 72-byte limit were silently truncated. →
  they are now rejected, measured in UTF-8 bytes.
- The login endpoint returned faster for an unknown address than for a known
  one, which allowed account enumeration by timing. → the password check now
  always runs, against a dummy hash when the address is unknown, and both
  cases return the same message.
- `POST /api/staff/tasks/{id}/checklist` used a _response_ schema as its
  request body, so a client had to send `id`, `task_id`, `done_at`… → it now
  takes a `ChecklistItemIn` body.
- The demo seed could create accounts with well-known development passwords in
  a production environment. → it refuses to run when `ARCH_ENVIRONMENT` is a
  production environment.
- The seed used `create_all`, which could create the schema without recording
  the Alembic revision, leaving the database in a state where a later
  `alembic upgrade head` failed. → the seed now runs the migrations itself.
- Demo accounts used `@arch.local` addresses, which the API correctly
  rejects (`.local` is a reserved domain) — signing in with them returned 422. → the demo addresses now use `example.com`.

**Known gaps (documented in `backend/README.md`, deployment responsibilities)**

- No rate limiting on sign-in or the contact form — must come from the
  reverse proxy.
- No e-mail verification on self-registration.
- No token revocation; sign-out is client-side only.
- No audit log of privileged actions (`ContentRevision` exists but is unused).
- Only the V-scale grade format is scored; other grade systems are ignored by
  the leaderboard.

**Open items**

- The frontend still reads only from the mock adapter — wiring it to this API
  is Task 2.
- The `drizzle/` directory from the Lovable import is still inert; it is left
  untouched rather than deleted, because removing it is not required by any

**Failure modes covered**

1. **No provider configured** — returns `None` immediately without attempting HTTP call; falls back to not-covered or deterministic structured answer.
2. **Provider request timeout** — `httpx.TimeoutException` caught, returns `None`, falls back to not-covered or deterministic answer.
3. **HTTP error responses** (4xx, 5xx) — `httpx.HTTPStatusError` caught via `httpx.HTTPError`, returns `None`, falls back.
4. **Network/transport errors** — `httpx.RequestError` caught via `httpx.HTTPError`, returns `None`, falls back.
5. **Malformed JSON responses** — `ValueError` caught during JSON parsing, returns `None`, falls back.
6. **Missing/unexpected response structure** — `KeyError`, `IndexError` caught during payload parsing, returns `None`, falls back.
6. **Empty/whitespace answer content** — explicit check after parsing rejects empty answers as failures, falls back.
7. **Unexpected provider exceptions** — broad catch-all for `KeyError`, `IndexError`, `ValueError` during parsing, returns `None`, falls back.
8. **Structured grounding data present but provider generation fails** — falls back to deterministic structured answer if available, otherwise not-covered.
9. **No usable FAQ or structured evidence available** — returns not-covered response with scope list.

**Fallback behavior**

- Direct FAQ matches (score ≥ 0.55) always return verbatim answer without LLM call.
- Structured deterministic answers (Task 6.2) take priority when single high-confidence source available.

### Task 1.2 — The member dashboard API (`DONE`)

**The change**

`GET /api/me/dashboard` used to answer with four numbers. It now answers with
the member's own picture of their climbing. The data is the member's own
records and the gym's own route list; nothing is estimated, and nothing is
invented.

- `backend/app/schemas/dashboard.py` (new) — the response contract:
  `DashboardOut`, `OutcomeCounts`, `GradeStat`, `RankingInfo` and
  `RecentAttempt`. `DashboardOut` moved out of `schemas/common.py`, which
  keeps the shared shapes and nothing more.
- `backend/app/services/dashboard.py` (new) — the rules: `count_active_routes`,
  `is_flash`, `build_outcomes`, `build_grade_stats`, `build_ranking`,
  `build_recent_attempts` and `build_dashboard`.
- `backend/app/api/member.py` — the endpoint now calls the service. The
  `/api/me/stats` alias answers with the same payload.
- `backend/app/services/climbing.py` — the scoring rule and the percentile rule
  are defined **once**, next to the calculation they describe, and travel with
  the ranking.
- `src/services/types.ts`, `src/services/arch.ts` — the frontend types and the
  mapping follow the new contract field for field.

**The rules, as implemented**

- **A flash is derived, not stored.** It is a send with exactly one attempt.
  It is a *subset* of the sends, never a third outcome, and the two are never
  added together.
- The outcome counts break the member's own logbook into **sends, flashes,
  projects and total attempts**.
- The record is **grouped by grade, easiest first**. A grade the member has
  only tried appears too, with its projects and no sends, so a project is
  never hidden by the absence of a send.
- The **ranking is the leaderboard's own**: sends only, one point per grade
  step (V0 = 1 point, V3 = 4 points), ties broken by number of sends, then
  best grade, then the date of the first send. A climber with no sends is not
  ranked. The dashboard reuses `build_leaderboard` and `rank_rows` rather than
  reimplementing them, so the two pages cannot disagree.
- The **percentile** is the share of ranked climbers who are **at or behind**
  the member's position, as a whole percentage. The top-ranked climber is at
  the 100th percentile; the last one at the lowest. It is `null` for a member
  who is not ranked, rather than zero.
- **A value that is not available is `null`, never zero.** No best grade, no
  rank, no percentile, no first climb. `has_activity` says whether the member
  has logged anything at all, so the interface can show an empty state rather
  than a page of zeroes.
- The **scoring rule and the percentile rule are sent with the ranking**, in
  words. The interface does not write the rule out again; it shows the one
  the numbers were actually worked out with.

### Task 1.3 — The route directory filters (`DONE`)

**The change**

The route directory used to fetch every route and narrow the list in the
browser. The filters are now applied by the backend, in the database, and the

- `backend/app/api/public.py` — `list_routes` takes `grade`, `wall`,

  `WallFilterOption` (new).
- `src/services/api.ts` — `RouteFilterParams` and `routeQueryString` (new):
  the filters are turned into a query string explicitly, each one a plain
  value. An unset filter is left out rather than sent as an empty string.
- `src/services/arch.ts` — `listFilteredRoutes` and `listRouteFilterOptions`
  (new), the `RouteFilters`/`RouteFilterOptions` types, and
  `filteredRoutesQuery(filters)`, whose key carries the filters, so a
  different filter is a different question. `Resource` gained
  `isUnavailable`, so "the list could not be loaded" is a state of its own.
  `allRoutesQuery`/`listAllRoutes` were removed: the status filter asks the
  backend for the statuses it wants.

  filtered query, the options from the API, and a **Clear filters** button
  that appears as soon as a filter is set.

  before it asks for a new list. The other filters are chosen, not typed, and
  are applied at once.
- `src/styles.css` — on a phone the filter bar stacks and each control is

**The decisions**

  the backend returned six, never a number taken from somewhere else.
- **An archived route is not shown as active.** The default listing is the
  active routes; "All statuses" brings the archived ones back with their own
  status, which the route card shows (task 1.5).
- **The search covers the name, the style and the wall**, which is what the
  search box promised before it moved to the backend.

### Phase 2A — Visual route-setting design (`DONE`)

`ROUTE_SETTING_DESIGN.md` was written from the code, not from assumptions:

- **What exists.** `Wall.image_url` holds a *reference* to the photograph
  (`/walls/placeholder-gym.jpg`, served from the frontend's `public/`); there
  is no image table, upload endpoint or pixel dimensions. `ClimbRoute` has
  `wall_id`, `wall_type`, `status`, `set_at`, `archived_at` and `image_url`,
  and no versioning. `Achievement` snapshots `route_name` and `grade`, so a
  member's attempts keep their meaning without route versions. Route CRUD is
  admin-only; `require_staff` and `require_admin` already exist.
- **What the design adds.** Three tables — `wall_holds` (normalised `x`, `y`,
  `width`, `height` on a wall photograph), `route_hold_sets`
  (draft/published/superseded), `route_holds` (ordered hold with
  start/middle/finish role) — plus one nullable
  `climb_routes.published_hold_set_id`. Holds belong to the wall, not the
  route, so one physical hold can serve several routes. Members read only
  through the published pointer of an active route.

### Phase 2B — Hold annotation backend (`DONE`)

The editor's data layer is committed on its own so the API can be verified
before any canvas code depends on it.

**Schema** (migration `83693e68129f`, on top of `9d1c4f8ab207`)

- `wall_holds` — one hand-drawn box on a wall photograph: `wall_id`, optional
  `label`, normalised `x`, `y`, `width`, `height`, `created_by_id`, with
  `CHECK` constraints that keep the box inside the image and forbid a
  zero-sized box.
- `route_hold_sets` — `route_id`, `status` (`draft` / `published` /
  `superseded`), the `wall_image_url` the boxes were drawn on, `published_at`.
- `route_holds` — `set_id`, `wall_hold_id`, 1-based `position` and `role`
  (`start` / `middle` / `finish`), unique per set on both position and hold.
- `climb_routes.published_hold_set_id` — nullable pointer to the sequence
  members may see. Only publishing moves it.

**API**

| Endpoint | Who |
| --- | --- |
| `GET/POST /api/staff/walls/{wall_id}/holds` | staff + admin |
| `PATCH/DELETE /api/staff/holds/{hold_id}` | staff + admin |
| `GET /api/staff/walls`, `GET /api/staff/walls/{wall_id}/routes` | staff + admin |
| `GET/PUT /api/staff/routes/{route_id}/hold-set` | staff + admin |
| `POST /api/staff/routes/{route_id}/hold-set/publish` | **admin only** |
| `GET /api/public/routes/{route_id}/holds` | anyone |

A draft becomes visible only through the publish action; the previous
published set is marked `superseded`, and an archived route returns no public
holds. The first hold in the sequence is the start and the last is the finish;
a supplied role that disagrees with the order is rejected. A new draft starts
from the published sequence, so a small correction does not mean drawing the
route again. A hold used by a published set cannot be deleted (409); removing
one from a draft closes up the positions.

### Phase 2B.3 — Undo for local editor changes (`DONE`)

The editor now has a bounded, reliable undo stack for the work that is still
local to the page. It restores the complete editor state captured before each
operation: the wall boxes, route membership and order, roles derived from that
order, and the selection. It never calls the draft save or publish endpoints.

**What was added**

- `src/components/arch/undo-history.ts` — immutable editor snapshots, a
  30-operation cap, and id remapping. Each entry also records the one wall hold
  that operation touched, so undo cannot delete or overwrite an unrelated box
  that another session created after the snapshot.
- `src/components/arch/route-setting.tsx` — snapshots are captured before
  creating, moving/resizing and deleting a box, and before adding, removing,
  reordering or changing the start/finish of a route hold. A new box creates a
  history entry only after the server accepts it; a failed create, update,
  delete, save or publish adds nothing to the history.
- Undo uses inverse operations: a created box is deleted, a deleted box is
  recreated, a moved/resized box is patched back to its previous geometry, and
  a membership/order/role change is applied locally with no server write.
  Deleting a box is refused for a published set or a route that still uses it,
  so undoing a delete cannot silently remove a member-visible hold.
- Recreating a deleted box produces a new server id. Every older snapshot is
  remapped to the new id, so the next undo still points at the real row.
- The Undo button is visible in the editor toolbar and disabled when there is
  nothing to undo and while any request is in flight. Its tooltip names the
  operation that will be undone.
- Ctrl+Z / Command+Z work only while the editing surface has focus and are not
  intercepted inside inputs, textareas, selects or contenteditable elements.
  The hold-box key handler now lets Ctrl/Cmd+Z bubble to the editor instead of
  swallowing it.
- The history is cleared when a draft save or publish succeeds, when a
  different route or wall is loaded, when the draft or holds are explicitly
  reloaded, and when a page reload starts a new baseline. A failed save leaves
  the history and every edit intact.

**Limitations**

- The shared wall-hold geometry question is still unresolved. A box's geometry
  lives on the wall row, not on each route's saved set. Undoing a move or
  resize is therefore a compensating `PATCH` to that shared row, not a local
  edit: every route that uses the box, including a published overlay, sees the
  restored geometry immediately. The editor warns when the box is in the
  published set, but undo cannot restore an independent copy for another
  route. The product decision remains documented under the shared-holds
  question in `ROUTE_SETTING_DESIGN.md`.
- Undoing a delete recreates the box with a new id and remaps this route's
  history. Other routes that referenced the old row are not restored. The
  backend's guard against deleting a box used by a published set or a route
  sequence prevents the common unsafe case, but it is not a full history
  rewrite.
- The history is intentionally in memory and is not persisted. Reloading the
  page, switching route or wall, reloading the draft/holds, or saving starts a
  new baseline. This prevents undo from crossing a persisted save, as required,
  but also means undo cannot repair an edit made in another tab or session.
- Undo has a 30-operation bound. There is no redo, and publication itself is
  not undoable.
- Undo of a box is a server write, not a local-only change. If a compensating
  request fails, the notice says so, the history remains, and the page can be
  reloaded to compare the server state; the local history is not a server
  transaction.
- PostgreSQL remains untested for this feature.

## 6. Production reliability (test_deploy branch)

**Status:** IN_PROGRESS — investigation and minimal fix applied; deployed verification pending.

**Root cause:** Cloudflare Python Workers runtime does not support concurrent synchronous database I/O. The get_db dependency was synchronous, causing "Cannot enter a promising task from inside another running promising task" errors under concurrent requests. ## 9. ARCH-Provided Content Policy

**Permanent policy for all agents and subagents:**

ARCH-specific business information must not be invented by AI agents or subagents. This includes, but is not limited to:

- FAQ questions and answers.
- Gym rules and safety policies.
- Opening hours and closure information.
- Prices and commercial conditions.
- Events and event schedules.
- Courses and course details.
- Services and facility information.
- Product descriptions and commercial claims.
- Any other factual information that requires confirmation from ARCH.

### Placeholder Behavior

Until ARCH supplies and confirms the relevant information:

- Keep CMS collections empty where no real content exists.
- Use clear empty states in admin and public interfaces.
- Use form placeholder text only as editing guidance, never as persisted content.
- Do not seed fictional FAQ, rules, events, courses, hours, prices, or services.
- Do not publish placeholder records.
- Do not allow placeholder text to become assistant grounding context.
- The assistant must report that the information has not yet been provided or published by ARCH, rather than guessing.

For FAQ specifically:
- A newly created FAQ must default to `is_published=false`.
- An admin must explicitly publish an entry after its content is supplied and approved.
- Preserve the state of existing records.
- Never bulk-unpublish existing approved content just to change the default.

For Rules:
- Preserve the existing distinction between `is_active` and `is_confirmed`.
- Do not invent safety or facility rules.
- Use empty-state guidance until ARCH supplies and confirms the actual rules.

Do not make a generic placeholder database record to represent missing content.
