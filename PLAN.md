**Security review — issues found and fixed**

- The production secret-key check only matched the exact string
  `"production"`. → now case-insensitive and also matches `"prod"`, and it is
  covered by a test that uses the environment variable.
- `CORS_ORIGINS=*` would have been combined with credentialed requests. →
  a wildcard is now rejected at start-up.
- Passwords longer than bcrypt's 72-byte limit were silently truncated. →
  they are now rejected, measured in UTF-8 bytes.
- The login endpoint returned faster for an unknown address than for a known
  one, which allowed account enumeration by timing. → the password check now
  always runs, against a dummy hash when the address is unknown, and both
  cases return the same message.
- `POST /api/staff/tasks/{id}/checklist` used a _response_ schema as its
  request body, so a client had to send `id`, `task_id`, `done_at`… → it now
  takes a `ChecklistItemIn` body.
- The demo seed could create accounts with well-known development passwords in
  a production environment. → it refuses to run when `ARCH_ENVIRONMENT` is a
  production environment.
- The seed used `create_all`, which could create the schema without recording
  the Alembic revision, leaving the database in a state where a later
  `alembic upgrade head` failed. → the seed now runs the migrations itself.
- Demo accounts used `@arch.local` addresses, which the API correctly
  rejects (`.local` is a reserved domain) — signing in with them returned 422. → the demo addresses now use `example.com`.

- No e-mail verification on self-registration.
- No token revocation; sign-out is client-side only.
- No audit log of privileged actions (`ContentRevision` exists but is unused).
- Only the V-scale grade format is scored; other grade systems are ignored by

### Task 2a — Production preview rendered without CSS (`DONE`)

**Reported symptom:** the production-build preview on port 8090 served the
pages without any styles, while the development site on port 8080 looked
correct.

**Diagnosis**

- The server-rendered HTML linked `/assets/styles-BKG1c1ua.css`, but the
  built stylesheet in `.output/public/assets` was `styles-BnTAO7e6.css`. The
  two hashes did not match, so the request 404'd and the page rendered as
  unstyled HTML.
- The cause was a stale `.output` directory: the Nitro/Cloudflare output is
  not fully emptied between builds, so repeated `bun run build` runs could
  leave a server bundle that referenced an asset hash from an earlier build
  while the public directory held the newer one. The build itself reported
  success, which is why the problem only showed up in the browser.

**Fix**

- `scripts/clean-output.mjs` removes `.output`, `dist`, `.nitro` and
  `.tanstack`; `bun run build` now runs it first, so every build is
  self-contained and repeatable. `bun run clean` runs it on its own.
- `scripts/check-styles.mjs` loads a page in a real browser and reports the
  computed styles, the applied stylesheets and any failed request, so a
  missing stylesheet cannot pass unnoticed again.

**Verification**

- `bun run build` twice in a row → the stylesheet hash in `.output/public`
  and the hash referenced by the server bundle are identical both times.
- `node scripts/check-styles.mjs http://localhost:8090` → the page is
  correctly styled: dark background `rgb(13, 14, 13)`, Barlow, sticky header,
  128px heading, and both stylesheets applied.

### Task 1.1 — Structured climbing walls and route types (`DONE`)

**The change**

The routes used to carry a free-text `zone` — the name of the wall, typed in
by hand. That cannot carry a photograph, cannot be filtered reliably and
cannot be checked. A wall is now a record of its own, and each route records
the type of its own problem.

- `backend/app/models/climbing.py` — a `walls` table (`name`, `description`,
  `image_url`, `sort_order`, `is_active`) and a `WallType` enum
  (`slab`, `vertical`, `overhang`, `roof`, `boulder`). `climb_routes` gains
  `wall_id` (a foreign key with `ON DELETE SET NULL`) and `wall_type`, and
  loses `zone`.
- **The type belongs to the problem, not to the wall.** A mixed wall holds
  both a slab and an overhang, so `wall_type` is a column of the route. This
  is a decision, not an accident.
- `backend/migrations/versions/9d1c4f8ab207_add_walls_and_route_types.py` —
  creates the walls, backfills them from the zones already in use, points

  known walls their type, and then drops `zone`. The downgrade puts the wall
  name back into `zone`, restoring the column as the required column it was.
- `backend/app/schemas/climbing.py` — `WallOut`, `WallCreateIn`, and the
  route responses carry `wall`, `wall_id` and `wall_type`.

### Task 1.2 — The member dashboard API (`DONE`)

**The change**

`GET /api/me/dashboard` used to answer with four numbers. It now answers with

  `RecentAttempt`. `DashboardOut` moved out of `schemas/common.py`, which
  keeps the shared shapes and nothing more.
- `backend/app/services/dashboard.py` (new) — the rules: `count_active_routes`,
  `is_flash`, `build_outcomes`, `build_grade_stats`, `build_ranking`,
  `build_recent_attempts` and `build_dashboard`.
- `backend/app/api/member.py` — the endpoint now calls the service. The
  `/api/me/stats` alias answers with the same payload.
- `backend/app/services/climbing.py` — the scoring rule and the percentile rule
  are defined **once**, next to the calculation they describe, and travel with
  the ranking.
- `src/services/types.ts`, `src/services/arch.ts` — the frontend types and the
  mapping follow the new contract field for field.

**The rules, as implemented**

- **A flash is derived, not stored.** It is a send with exactly one attempt.
  It is a *subset* of the sends, never a third outcome, and the two are never
  added together.
- The outcome counts break the member's own logbook into **sends, flashes,
  projects and total attempts**.
- The record is **grouped by grade, easiest first**. A grade the member has
  only tried appears too, with its projects and no sends, so a project is
  never hidden by the absence of a send.
- The **ranking is the leaderboard's own**: sends only, one point per grade
  step (V0 = 1 point, V3 = 4 points), ties broken by number of sends, then

  reimplementing them, so the two pages cannot disagree.

  the member's position, as a whole percentage. The top-ranked climber is at

  has logged anything at all, so the interface can show an empty state rather
  than a page of zeroes.

- **What exists.** `Wall.image_url` holds a *reference* to the photograph

### Phase 2B — Hold annotation backend (`DONE`)

The editor's data layer is committed on its own so the API can be verified
before any canvas code depends on it.

**Schema** (migration `83693e68129f`, on top of `9d1c4f8ab207`)

- `wall_holds` — one hand-drawn box on a wall photograph: `wall_id`, optional
  `label`, normalised `x`, `y`, `width`, `height`, `created_by_id`, with
  `CHECK` constraints that keep the box inside the image and forbid a
  zero-sized box.
- `route_hold_sets` — `route_id`, `status` (`draft` / `published` /
  `superseded`), the `wall_image_url` the boxes were drawn on, `published_at`.
- `route_holds` — `set_id`, `wall_hold_id`, 1-based `position` and `role`
  (`start` / `middle` / `finish`), unique per set on both position and hold.
- `climb_routes.published_hold_set_id` — nullable pointer to the sequence
  members may see. Only publishing moves it.

**API**

| Endpoint | Who |
| --- | --- |
| `GET/POST /api/staff/walls/{wall_id}/holds` | staff + admin |
| `PATCH/DELETE /api/staff/holds/{hold_id}` | staff + admin |
| `GET /api/staff/walls`, `GET /api/staff/walls/{wall_id}/routes` | staff + admin |
| `GET/PUT /api/staff/routes/{route_id}/hold-set` | staff + admin |
| `POST /api/staff/routes/{route_id}/hold-set/publish` | **admin only** |
| `GET /api/public/routes/{route_id}/holds` | anyone |

A draft becomes visible only through the publish action; the previous
published set is marked `superseded`, and an archived route returns no public
holds. The first hold in the sequence is the start and the last is the finish;
a supplied role that disagrees with the order is rejected. A new draft starts
from the published sequence, so a small correction does not mean drawing the
route again. A hold used by a published set cannot be deleted (409); removing
one from a draft closes up the positions.

### Phase 2B.3 — Undo for local editor changes (`DONE`)

The editor now has a bounded, reliable undo stack for the work that is still
local to the page. It restores the complete editor state captured before each
operation: the wall boxes, route membership and order, roles derived from that
order, and the selection. It never calls the draft save or publish endpoints.

**What was added**

- `src/components/arch/undo-history.ts` — immutable editor snapshots, a
  30-operation cap, and id remapping. Each entry also records the one wall hold
  that operation touched, so undo cannot delete or overwrite an unrelated box
  that another session created after the snapshot.
- `src/components/arch/route-setting.tsx` — snapshots are captured before
  creating, moving/resizing and deleting a box, and before adding, removing,
  reordering or changing the start/finish of a route hold. A new box creates a
  history entry only after the server accepts it; a failed create, update,
  delete, save or publish adds nothing to the history.
- Undo uses inverse operations: a created box is deleted, a deleted box is
  recreated, a moved/resized box is patched back to its previous geometry, and
  a membership/order/role change is applied locally with no server write.
  Deleting a box is refused for a published set or a route that still uses it,
  so undoing a delete cannot silently remove a member-visible hold.
- Recreating a deleted box produces a new server id. Every older snapshot is
  remapped to the new id, so the next undo still points at the real row.
- The Undo button is visible in the editor toolbar and disabled when there is
  nothing to undo and while any request is in flight. Its tooltip names the
  operation that will be undone.
- Ctrl+Z / Command+Z work only while the editing surface has focus and are not
  intercepted inside inputs, textareas, selects or contenteditable elements.
  The hold-box key handler now lets Ctrl/Cmd+Z bubble to the editor instead of
  swallowing it.
- The history is cleared when a draft save or publish succeeds, when a
  different route or wall is loaded, when the draft or holds are explicitly
  reloaded, and when a page reload starts a new baseline. A failed save leaves
  the history and every edit intact.

## 5. Decisions taken (and why)

| Decision                                                                                 | Rationale                                                                                                                         |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Keep TanStack Start + Tailwind v4 + TanStack Router                                      | Existing Lovable stack; the brief says not to migrate without cause.                                                              |
| New Python/FastAPI backend in `backend/`                                                 | The brief and README both prefer FastAPI + PostgreSQL. The existing Supabase scaffold has no tables and is not a working backend. |
| SQLAlchemy 2.0 + Alembic, PostgreSQL 18.6 as the normal local database with SQLite test/recovery fallback | PostgreSQL is the deployment target and now the verified local workflow; SQLite keeps the ordinary test suite fast and isolated. |
| Frontend talks to the backend through `src/services/api.ts`                              | Keeps mock data isolated behind one replaceable boundary; the existing UI does not need rewriting.                                |
| Keep the mock adapter as an explicit offline fallback                                    | The site must still render when the backend is not running, and mock data must stay clearly labelled.                             |
| Passwords hashed with `bcrypt`; JWT access tokens issued by the backend                  | Required by the brief; avoids adding a JS auth dependency to the frontend.                                                        |
| The role is read from the database on every request, never from the token                | A stale or tampered token claim must not be able to grant access.                                                                 |
| The seed runs the Alembic migrations instead of `create_all`                             | Keeps the schema and the recorded migration revision from drifting apart.                                                         |
| Prices, courses and events are seeded empty; rules are seeded as _drafts_                | ARCH has not supplied these yet, so the site must show a labelled placeholder rather than invented numbers.                       |
| The service layer returns a `Resource<T>` that names its data source                     | Sample data must never be presented as live information; the banner and the badges read the same field.                           |
| Reads never throw, writes do                                                             | A page must stay browsable when the backend is down, but a message that failed to send has to say so.                             |
| Removed `src/client.tsx`                                                                 | The framework's default client entry is the only one that mounts the app; the file added in Task 1 silently disabled hydration.   |
| AI provider credentials stay server-side; no provider configured → grounded FAQ fallback | The brief forbids exposing keys and forbids pretending a fallback is live AI.                                                     |
| The wall type is a property of the route, not of the wall                                          | A mixed wall holds both a slab and an overhang, so one wall can carry problems of different types.                               |
| SQLAlchemy stores the enum **name**; the API exposes the lower-case value                             | The database has to hold what SQLAlchemy reads back. The API stays readable, and the two are kept apart deliberately.            |
| An archived route keeps its place in the public directory, with its status shown                     | A climber who follows an old link is told the route has been taken down, rather than being shown a page that does not exist.     |
| The dashboard reuses the leaderboard's calculation instead of reimplementing it                     | Two pages that show the same ranking must never tell a member different stories.                                                |
| The scoring rule and the percentile rule are defined in the backend and sent with the ranking        | The interface cannot state a rule that differs from the one the numbers were worked out with.                                   |
| A value that is not available is `null`, never zero                                                | "No best grade yet" and "a best grade of V0" are different facts, and a new member should not be shown a page of zeroes.            |

### Known limitations

- **PostgreSQL is the normal local database, but a production PostgreSQL
  deployment and PostgreSQL CI are still unexercised.** Migrations, repeatable
  seeding, live HTTP flows, restart persistence and the frontend were verified
  against local PostgreSQL 18.6. The ordinary test suite deliberately uses an
  isolated SQLite database, and the PostgreSQL integration tests require an
  explicitly configured server; see
  [POSTGRESQL_COMPATIBILITY.md](POSTGRESQL_COMPATIBILITY.md).
- **The deployment has not been performed.** The build produces a Cloudflare
  Worker that has not been deployed.
- **No rate limiting and no e-mail verification.** Both belong in the proxy in
  front of the API, and both are called out in the deployment guide.
- **Tokens cannot be revoked.** A token issued before a password change stays
  valid until it expires.
- **No file upload.** Media is referenced by URL.
- **The shop has no checkout.** The catalogue is informational.
- **The placeholders are still placeholders.** The prices are empty, the
  opening hours say "to be confirmed", the rules are marked as drafts and the
  photographs are generated artwork.
- The live language-model path for the assistant has not been exercised
  against a provider.
