### Critical gaps found in the import

1. **`src/styles.css` was missing** — every component references custom classes
   (`site-header`, `hero-photo`, `route-card`, `workspace`, …) that only existed in that file. The app could
   not build. → Reconstructed from the class inventory.
2. **`src/router.ts` was missing** — TanStack Start requires a router entry; the build failed to resolve it.
3. **`src/server.ts` was missing** — referenced by `vite.config.ts` (`tanstackStart.server.entry = "server"`).
   `src/lib/error-capture.ts` and `src/lib/error-page.ts` exist purely to support it.
4. **`src/client.tsx` / `src/start.ts` were missing** — optional entries; recreated.
5. **Both images were zero bytes** (`src/assets/arch-gym.jpg`, `src/assets/climbing-shoes.jpg`) — every hero and
   product image was broken. → Placeholder artwork generated by `scripts/generate_placeholder_images.py`.
6. **`public/favicon.svg` was missing** although `__root.tsx` links to it.
7. **`drizzle/schema.ts` is empty** and there are no migrations — the Drizzle/Supabase scaffolding is inert.
8. **All data is mock.** `src/services/arch.ts` is a hard-coded mock adapter; the UI labels itself
   "sample data / preview" throughout.
9. **`bun run lint` failed on the import** — 432 `prettier/prettier` errors (compact one-line style vs. the
   repository Prettier config, plus CRLF line endings). Fixed by normalising formatting.
10. **`.env` contains a real Supabase project key** and is git-ignored, but there was **no `.env.example`**.

## 5. Decisions taken (and why)

| Decision | Rationale |
| --- | --- |
| Keep TanStack Start + Tailwind v4 + TanStack Router | Existing Lovable stack; the brief says not to migrate without cause. |
| New Python/FastAPI backend in `backend/` | The brief and README both prefer FastAPI + PostgreSQL. The existing Supabase scaffold has no tables and is not a working backend. |
| SQLAlchemy 2.0 + Alembic, PostgreSQL target with SQLite dev fallback | No PostgreSQL server exists in this environment; the same models/migrations run on both. |
| Frontend talks to the backend through `src/services/api.ts` | Keeps mock data isolated behind one replaceable boundary; the existing UI does not need rewriting. |
| Keep the mock adapter as an explicit offline fallback | The site must still render when the backend is not running, and mock data must stay clearly labelled. |
| Passwords hashed with `bcrypt`; JWT access tokens issued by the backend | Required by the brief; avoids adding a JS auth dependency to the frontend. |
| AI provider credentials stay server-side; no provider configured → grounded FAQ fallback | The brief forbids exposing keys and forbids pretending a fallback is live AI. |
